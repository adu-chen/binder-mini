# Binder Mini APC

## 1. 项目身份

Binder Mini 是一个面向 GitHub 开源开发的本地优先 AI 文档编辑器最小核心。

项目参考 `/Users/imatstarbucks/binder-core` 的产品事实和技术事实，但不直接继承旧 `binder-mini` 实现，也不把 `binder-core` 旧文档原样作为本项目权威源。

核心交互：用户通过对话让 AI 生成文档修改 diff，用户接受或拒绝后才写入文件。

应用形态：Tauri 2 + React + TypeScript + Rust 桌面应用。

数据边界：workspace 是用户选择的本地目录，是所有文件操作、搜索、diff 和上下文读取的边界。

版本管理：项目使用 git 管理版本，面向 GitHub 仓库协作、审查、发布和开源治理。

明确不做：多人协同、云服务、Office 套件、知识库平台、插件市场、通用聊天机器人。

## 2. 开发方法论

项目采用文档先行、规则驱动、状态机驱动开发。

本项目在 ADU 两阶段模型内启用四级项目门禁：

- G1：需求描述完成门禁
- G2：技术设计完成门禁
- G3：开发计划完成门禁
- G4：开发实现验证门禁

未通过 G1，不得进入技术设计。未通过 G2，不得进入开发计划。未通过 G3，不得进入代码实现。未通过 G4，不得进入 READY、合入或发布。

AI 可以提出进入下一阶段建议，但不得自行宣布进入下一阶段。人类要求越级实现时，AI 必须执行 ADP Phase Gate Check；门禁不满足时，触发 ADP `SC-06 PHASE_GATE_BLOCKED` 或 `SC-07 MAPPING_CHAIN_BROKEN`，不得进入代码修改。

技术设计文档是代码实现的最终规则来源。代码实现不得脱离技术设计文档中定义的架构、协议、接口、状态机、验收标准、测试方案和已注册规则体系。

完整规则链条为：

`REQ -> REQ_MAP -> RULE / CHAIN / CONSTRAINT / TERM -> STATE_MACHINE（如适用） -> Plan Item -> Issue Trace -> @GOV -> Test covers -> Task Runtime Report`

AI 可以生成草案、实现代码、补充标注、执行审计，但不得绕过 ADP Scope、Stop Condition 和 Task Runtime Report。

设计文档与代码冲突时，设计文档优先；AI 不得为错误实现反向修改设计文档。

## 3. 文档体系声明

L0 治理控制文档包括：

- `ADU.md`
- `ADP.md`
- `CLAUDE.md`
- APC：`docs/00_core/A-CORE-C-P-01_APC.md`
- ADUS：`docs/00_core/A-CORE-C-R-01_ADUS.md`

项目业务文档采用三层职责体系。三层职责固定，具体文件名视项目主题和阶段命名。

### 3.1 功能需求描述文档层

职责：说明产品要做什么、为什么做、服务谁、边界是什么。

典型文档包括：

- 产品定义
- 需求描述
- 专项功能描述
- 用户场景
- 功能边界
- 术语边界

该层文档定义产品意图和需求边界，不直接替代技术实现规则。

需求描述文档必须使用 ADU `<!-- REQ -->` 标注块声明需求层规则。需求层规则不是代码实现规则来源，代码不得直接映射 `REQ-*`。

### 3.2 技术设计文档层

职责：说明系统如何实现，是代码实现的最终规则来源。

典型文档包括：

- 架构设计
- 技术方案
- 接口规范设计
- Tauri command 协议
- 数据结构与状态结构
- 状态机设计
- 相关协议设计
- 专项开发设计
- 验收标准
- 测试方案

规则、链路、模块、术语和跨模块约束优先在技术设计文档中定义。代码实现必须承接技术设计文档中的 `<!-- RULE -->`、`<!-- CHAIN -->`、`<!-- MODULE -->`、`<!-- TERM -->`、`<!-- CONSTRAINT -->` 标注块。

需求到技术规则的映射必须通过 ADU `<!-- REQ_MAP -->` 标注块、需求规则映射矩阵或 APC 认可的等价映射关系声明。

### 3.3 开发计划文档层

职责：说明项目如何落地、按什么顺序开发、如何验证、如何发布。

典型文档包括：

- 项目落地顺序
- 实施计划
- 版本管理计划
- 里程碑计划
- 发布部署计划
- Git 分支与合并策略
- 开源发布准备清单

计划文档不得替代功能需求或技术设计文档作为代码规则来源；若计划变更影响实现规则，必须同步更新对应技术设计文档。

ADUS 只能由 `npm run governance:generate` 生成，禁止人工编辑自动生成区。

## 4. 阶段门禁与完成标准

### 4.1 G1 需求描述完成门禁

需求描述文档完成后，才允许进入技术设计。

完成标准：

- 每个功能有稳定 `REQ-*` 编号。
- 每个功能有清晰功能流程图或等价流程表。
- 每个功能描述目标、用户、入口、输入、输出、主流程、分支流程、异常路径和终态。
- 功能边界明确：做什么、不做什么、依赖什么、与哪些模块交互。
- 各功能模块职责清晰，不重叠、不悬空。
- 需求逻辑自洽，不存在互相冲突的规则。
- 不能细化的内容必须显式暴露，不能用模糊文字掩盖。
- 每条 active 需求必须进入后续设计映射，或显式标记 blocked / deferred / needs_human_decision。
- 需求文档不得直接作为代码实现规则来源。

需求阶段必须包含问题暴露清单，分类如下：

| 类型 | 含义 |
|------|------|
| REQ_GAP | 需求细节缺失 |
| BOUNDARY_OPEN | 功能边界未闭合 |
| REQ_CONFLICT | 需求之间存在冲突 |
| FLOW_INCOMPLETE | 功能流程不完整 |
| ACCEPTANCE_MISSING | 验收标准缺失 |
| NEEDS_HUMAN_DECISION | 需要人类裁决 |
| DESIGN_RISK | 后续设计存在风险 |

需求阶段不要求一次性覆盖全部实现细节，但必须把问题暴露出来。影响设计正确性的开放问题未关闭或未显式延期时，不得通过 G1。

功能流程图的覆盖要求和格式规范见 §5。

### 4.2 G2 技术设计完成门禁

技术设计文档完成后，才允许进入开发计划。

完成标准：

- 每个功能有清晰落地方案。
- 每个功能承接明确的 `REQ-*`。
- 每个功能映射到 `RULE / CHAIN / CONSTRAINT / TERM`。
- 每个功能说明主责模块、参与模块、跨模块交互。
- 包含整体架构和技术路线。
- 包含数据结构、状态结构、接口协议、Tauri command、service API。
- 包含错误处理、异常路径、恢复策略。
- 包含测试方案和通过条件。
- 包含验收标准。
- 包含可豁免实现债务。
- 包含技术盲区清单。
- 对多层交互或状态化功能，必须有状态机约束方案。

每个功能设计至少应覆盖：

```text
功能 ID：
承接需求：
主责模块：
参与模块：
主链路：
规则来源：
功能流程：
数据结构：
接口协议：
状态变化：
异常处理：
测试方案：
验收标准：
可豁免债务：
技术盲区：
```

技术设计文档中已注册的 RULE / CHAIN / CONSTRAINT / 状态机，是代码实现的唯一规则来源。开发计划、代码实现、@GOV 标注、测试 covers 必须承接技术设计文档。代码不得直接承接自然语言需求。计划文档不得替代技术设计文档成为规则来源。

设计与代码冲突时，默认设计优先。若设计不完整，必须回退设计阶段补齐。不得用代码实现反向补设计漏洞，不得为错误实现反向修改设计文档。

### 4.3 G3 开发计划完成门禁

开发计划完成后，才允许进入代码实现。

开发计划必须依托技术设计，不得直接依托需求文档写实现路径。

完成标准：

- 每个计划条目承接明确 `REQ-*`。
- 每个计划条目承接明确 `RULE / CHAIN / CONSTRAINT`。
- 每个计划条目说明是否承接状态机。
- 明确实现顺序和前后依赖依据。
- 明确文件范围。
- 明确测试文件和测试路径。
- 明确验收条件。
- 关键复杂设计必须给出代码示例或伪代码。
- 风险、债务、延期项必须显式列出。

计划条目模板：

```text
Plan Item：
承接 REQ：
承接 RULE：
承接 CHAIN：
承接 CONSTRAINT：
承接状态机：
实现文件：
测试文件：
前置依赖：
实现步骤：
关键代码示例：
验收条件：
风险 / 债务：
```

若计划阶段发现设计缺口，必须回退 G2，不得在计划中临时补实现规则。

### 4.4 G4 开发实现验证门禁

代码实现阶段必须验证规则声明真实性。

完成标准：

- 所有在 ADU §5.1 负空间扫描范围内的代码块有 `@GOV` 或 triage 记录。
- `@GOV rules` 必须引用已注册技术规则，不得引用 `REQ-*`。
- `@GOV boundary` 必须描述代码真实输入、输出、副作用。
- `@GOV` 不得成为装饰性标注。
- 测试 `// covers: BR-*` 必须有实际断言支撑。
- 状态机功能必须有状态转移测试。
- 多层交互功能必须至少有一条跨层验证路径。
- `npm run governance:audit` 通过。
- 相关测试通过。
- Task Runtime Report 必须说明规则链是否完整。

真实性缺口分类：

| 类型 | 含义 |
|------|------|
| ANNOTATION_ONLY | 只有标注，没有实际行为 |
| RULE_BEHAVIOR_MISSING | 规则行为缺失 |
| BOUNDARY_FALSE | boundary 与代码行为不一致 |
| TEST_ASSERTION_WEAK | covers 有声明但断言不足 |
| STATE_MACHINE_DRIFT | 代码状态转移偏离状态机 |
| MAPPING_DECORATIVE | 映射链只是装饰性引用 |

上述分类先由 AI 语义审计识别，不要求第一阶段脚本全自动实现。影响正确性、范围或治理闭环时，必须触发 ADP Stop Condition。

## 5. 功能流程图要求

每个功能必须有功能流程图或等价流程表。

流程图至少覆盖：

- 用户入口
- 前置条件
- 主流程
- 分支流程
- 异常路径
- 人类确认点
- 模块交互点
- 数据读写点
- 阻断条件
- 终态

多模块功能必须标出模块边界，例如：

```text
UI -> Store -> Service -> Tauri Command -> Rust -> File System
UI -> Agent -> Tool Call -> Workspace Reader -> Diff
```

推荐使用 Mermaid；无法使用 Mermaid 时，必须使用 Flow Table：

```text
step_id | actor | input | action | output | next_step | exception
```

## 6. 状态机设计与 SSOT

状态机不是所有功能强制，但以下功能必须有状态机设计：

- 多层交互功能
- 跨模块协作功能
- 有明确状态生命周期的功能
- 涉及打开、关闭、保存、发送、流式响应、接受、拒绝、过期等状态变化的功能
- 涉及 UI / Store / Service / Tauri / Rust / 文件系统多层协作的功能

状态机设计必须包含：

```text
machine_id
owner_module
scope
context
initial_state
states
terminal_states
events
transitions
guards
actions / effects
error_states
recovery_paths
forbidden_transitions
acceptance_criteria
test_matrix
```

完成标准：

- 所有合法状态被穷举。
- 所有终态明确。
- 所有事件有来源。
- 所有合法转移有条件。
- 所有非法转移有阻断策略。
- 所有副作用有归属。
- 所有异常路径有恢复或终止策略。
- 状态转移有测试矩阵。

对于被声明为状态机约束的功能，状态机设计是状态、事件、转移、副作用和终态的唯一真值。代码、测试、开发计划、@GOV 标注必须承接状态机定义。

## 7. 人类阶段晋级指令与自然语言响应

阶段晋级必须来自人类明确语义。

有效指令示例：

```text
需求阶段通过，进入技术设计
开始技术设计
设计完成，进入开发计划
可以进入代码实现
开始实现该功能
```

无效或不足指令示例：

```text
继续
优化一下
完善一下
看看能不能做
直接做吧
```

当指令不明确或越级时，AI 必须判断当前阶段、检查前置门禁、输出缺口，并在必要时触发 ADP `SC-06 PHASE_GATE_BLOCKED` 或 `SC-07 MAPPING_CHAIN_BROKEN`，不得进入代码修改。

AI 处理人类自然语言指令的顺序：

1. 识别人类真实语义。
2. 判断任务所属治理阶段。
3. 匹配功能链条。
4. 匹配 REQ / RULE / CHAIN / MODULE / STATE_MACHINE。
5. 判断阶段门禁是否满足。
6. 若满足，执行。
7. 若不满足，指出缺口并暂停。

AI 不得只按字面局部执行，必须以完整功能链条为基础响应。

## 8. ADU/ADP 启用声明

本项目全面启用 ADU / ADP / CLAUDE 治理。

强制治理模块：

- `CORE`：项目核心与治理
- `SYS`：系统架构与协议
- `WS`：workspace 生命周期与文件管理
- `ED`：编辑器运行时
- `AG`：Agent 与工具调用
- `DE`：diff 生成、审阅、终态

`governance:audit` 作为阻断性检查：audit 失败且当前 Scope 内无法修复时，不得进入 READY 状态。

代码阶段核心链路必须添加块注释格式 `/** @GOV ... */`。

测试文件必须使用 `// covers: BR-...` 声明规则覆盖。

本项目使用 ADU 提供的 `REQ`、`REQ_MAP` 和可选 `STATE_MACHINE` 标注结构。状态机是否强制、功能流程图是否强制、文档完整性标准和项目级 SSOT 由本 APC 定义。

本项目使用 ADP 提供的 `governance_phase`、Phase Gate Check、`SC-06 PHASE_GATE_BLOCKED`、`SC-07 MAPPING_CHAIN_BROKEN`、阶段化补充验证，以及 Task Runtime Report 的 `phase_gate` / `mapping_chain` 字段。

## 9. AI 执行边界与工作风格

AI 不得自主决定以下事项：

- 改变产品定位
- 扩大明确不做的范围
- 修改 APC 文档内容（须人类明确要求）
- 修改 ADU.md、ADP.md、CLAUDE.md
- 人工编辑 ADUS 自动生成区
- 在 Stop Condition 未解除时继续推进
- 将 `binder-core` 规划性文档误判为当前实现真值
- 跳过状态机设计直接实现适合状态化表达的核心功能链
- 将计划文档当作代码规则来源替代技术设计文档
- 创建无法追溯到技术设计文档已注册规则体系的游离代码块

AI 不得讨好性回复或讨好性执行。AI 必须从专业成熟工程师角度审查人类决策。人类决策与项目目标、技术事实、规则链冲突时，AI 必须直接指出。AI 不得弱化风险、隐藏阻断、伪造完成状态，或为了继续推进而把设计漏洞转嫁给代码实现。项目最终落地质量优先于表面顺从。

AI 必须暂停等待人类裁决的情况：

- 模块职责归属不明确
- 规则与已有规则冲突
- 设计文档与代码实现冲突
- Scope 需要扩展
- 缺少静态规则、链路、模块、术语或状态机定义
- 发现代码块无法追溯到技术设计文档已注册规则体系
- 治理审计失败且当前 Scope 内无法修复

## 10. 版本与变更管理

项目使用 git 作为版本管理工具，面向 GitHub 开源协作。

推荐分支策略：

- `main`：稳定主线，接受通过治理与测试门禁的版本
- `dev`：日常集成分支
- `feature/*`：功能开发分支
- `fix/*`：缺陷修复分支

合并原则：

- 影响代码实现的变更必须能追溯到技术设计文档规则
- 涉及核心链路的 PR 必须通过治理审计和相关测试
- 文档变更影响规则时，必须刷新 ADUS 并检查 @GOV 引用
- 发布前必须完成版本说明、验收记录和发布部署检查

APC 被新版取代时，旧版必须改为 `X` 状态。
